# 产品复盘：让长期对话的记忆召回稳定且可信

## 项目边界

这不是一个从零发明的“新向量数据库”。开源 LMC5 已经提供分层长期记忆、原始事件、结构化记忆与向量召回等架构参考。我在长期使用 AI 助手的过程中，重点处理的是召回进入真实对话后暴露出来的产品问题：中文短词会漏、弱向量会乱命中、每轮注入长度不稳定、摘要与原话缺少可验证关系。

本仓库是独立、脱敏的最小实现，只展示我定义的产品规则和验收方法，不包含上游源码或私人生产系统。

## 问题是怎样出现的

最早接入向量召回后，“能搜到相关记忆”并不等于体验已经可靠。

第一类问题是中文表达。两三个字的人名、物品名和主题词信息量很高，但向量模型不一定给出足够高的相似度。例如用户自然地说“和教练出去吃饭”，真正重要的实体可能只有“教练”两个字。如果还在召回层叠加长度阈值，正确结果很容易在进入上下文前被过滤掉。

第二类问题是误召回。向量可以找到语义上“有点像”的内容，却无法单独证明这条旧记忆适合影响当前回答。纯粹降低阈值虽然能提高命中率，也会把无关内容塞进每一轮对话。

第三类问题是上下文成本。即使找对了记忆，把多条完整正文全部注入也会让每轮 Token 消耗明显波动。长期对话最需要的不是偶尔一次召回很多，而是持续、稳定地提供少量有效信息。

最后，即使一条摘要看起来合理，用户仍然可能需要确认“当时到底是怎么说的”。把所有原始聊天都注入并不合适，但完全失去原话又会让摘要变成无法核实的二手信息。

我因此把问题重新定义为：**怎样在固定上下文预算内，让字面证据和语义召回互相补位，并让少量重要记忆可以回到原话验真。**

## 我做出的产品判断

### 1. 召回不是越多越好

我把普通召回限制为最多 3 条、总计 1200 字。它们是产品合同，不是排序算法可以自行突破的建议值。

这个选择牺牲了一部分“多给模型一点也许有用”的可能性，换来更稳定的每轮成本和更少的上下文污染。真正需要更多信息时，应由模型或用户按编号主动展开，而不是在每次对话里预付全部成本。

### 2. 中文短词应成为确定性证据

标题、关键词和实体别名中出现的两字以上词组，可以直接证明当前消息与某条记忆存在明确联系。它们不应先经过一个偏向长文本的阈值，再等待向量模型批准。

因此，中文词组和实体别名可以独立触发候选；向量仍然参与排序，但不再垄断召回入口。

### 3. 向量适合补充，不适合独裁

当用户更换措辞、使用近义表达或只描述结果时，字面搜索会失效，这正是向量的价值。最终策略是：

- 有明确字面或实体证据时，允许召回并记录证据来源。
- 没有字面证据时，向量必须达到较高阈值。
- 字面与向量共同命中时提高置信度。
- 只有弱向量相似时拒绝结果，而不是为了凑满 Top-K 强行返回。

这使“召回为空”成为一种合法结果。与其每轮都显得记得很多，不如在证据不足时不打扰当前回答。

### 4. 摘要和原文必须分层

短摘要适合进入每轮上下文，完整原文适合保存事实和细节，两者用途不同。摘要不能覆盖长期记忆正文，并且必须绑定生成时的正文 SHA-256；正文发生变化后，旧摘要不能继续被当成当前版本使用。

如果摘要缺失或已过期，系统回退到有界正文，而不是继续使用一段可能已经错误的旧摘要。

### 5. 原文绑定必须是明确选择

“最近一句话”或“语义上最相似的一句话”不一定是这条记忆真正的依据。因此原文绑定只接受两种方式：唯一精确原话，或已经定位好的明确消息 ID。

重复的“好的”“知道了”必须先搜索和确认位置，系统不能猜。绑定表只保存外部消息引用和内容 SHA-256，不复制聊天正文；普通召回也只提示证据是否存在。需要核实时再读取，并检查原文是否变化或缺失。

## 从需求到方案

最终链路被拆成四层：

1. **输入去噪**：先剥离渠道包装、消息 ID 和结构标签；纯表情、短确认和标点直接跳过。
2. **多路候选**：中文词组、标题、关键词、实体别名与向量分别提供候选和证据。
3. **门控与预算**：拒绝弱向量噪音，融合多路证据，排序后应用 Top-K、单条长度与总字符上限。
4. **轻量注入与按需验真**：优先注入仍与正文摘要一致的短摘要；原话只在明确请求时读取并校验。

生产实现还把向量维护纳入 Nightly：新写入和正文更新会生成向量，缺失向量由定时任务补齐，正文变化会使旧向量和旧摘要失效。这样召回质量不是靠一次性迁移维持，而是成为长期运行的数据生命周期。

## 使用前后的变化

改造前，用户体验更像“每次都进行一次不可解释的语义搜索”：短中文主题偶尔漏掉，调低阈值后又容易出现无关结果，返回正文数量也不稳定。

改造后，用户可以感受到几个稳定特征：

- 每轮召回体积有固定上限，不会突然出现一大段历史。
- 中文短词和人名可以直接命中，不必等待向量模型理解。
- 改写后的表达仍能由向量补充。
- “嗯嗯”“好的”等消息不会触发无意义计算。
- 召回结果可以说明来自字面、实体、向量还是多路互证。
- 对重要记忆有疑问时，可以回到被绑定的具体原话，而不是只相信摘要。

截至 2026 年 10 月，个人生产系统中 675 条有效记忆已全部具备向量，664 条具备独立短摘要；37 条主动选择的高价值记忆绑定了 80 条原话证据。这些数据证明链路长期在运行，但不等于公开基准上的召回质量结论。

## 为什么这不只是技术功能

如果把目标写成“接入 pgvector”，实现完成后很难判断产品是否变好。我的验收对象始终是用户体验：

- 每轮 Token 是否稳定。
- 中文自然表达能否找到正确主题。
- 无关词是否保持零召回。
- 召回内容是否足够短，且仍保留下一步展开入口。
- 摘要和原文之间是否存在可核验关系。
- 外部向量超时或失败时，字面召回是否仍能继续工作。

这让向量数据库成为实现手段，而不是项目目标。

## 验证与仍未解决的问题

公开示例通过了低信息跳过、渠道去噪、中文两字实体、向量改写补充、弱向量拒绝、多路证据、摘要失效、字符预算、精确原文绑定和完整性校验测试。

仍需诚实说明：

- 本仓库的无依赖 `HashingEmbedder` 只是接口和融合演示，不具备生产语义模型的泛化能力。
- 1200 字和最多 3 条来自个人使用体验，不是对所有用户最优的固定答案。
- 字符数只是 Token 成本的近似控制。
- 当前没有公开人工标注集，无法给出 Recall@K、MRR 或与纯向量方案的严格对照实验。
- 生产延迟受 embedding 服务、网络和向量库规模影响，个人观测不能直接外推。
- 原文证据只能证明绑定消息是否仍与摘要一致，不能自动证明摘要中的每个推论都正确。

目前已补充第一版 4 条合成合同用例，用于验证短实体、同义改写和无关负例下的机制差异，并对比纯字面、无拒绝阈值的最近邻 Top-1 与混合门控。下一步将扩展更大的人工标注中文查询集，并加入 Recall@K、MRR 等正式对照指标。

## 我的职责

- 从长期真实使用中发现中文短词漏召回、弱向量污染和上下文成本波动。
- 将目标从“接入向量库”重新定义为“固定预算内的少量可信召回”。
- 定义字面／实体优先、向量补充、跨通道互证和弱结果拒绝规则。
- 定义最多 3 条、1200 字、短摘要注入与按编号展开的产品合同。
- 提出逐记忆原文绑定，并坚持唯一精确原话或明确消息 ID、引用与正文分离、按需回读验真。
- 依据真实中文表达、负例和长期 Token 体感参与验收。
- 代码实现和自动化测试由 AI 完成；我没有独立编写这些代码。
