# Bounded Hybrid Memory Recall

一个面向长期运行 AI 助手的**有界中文混合召回与原文证据层**。

它解决的不是“有没有向量数据库”，而是更贴近真实使用的问题：如何让每轮召回的 Token 消耗稳定、中文短词能够被识别、语义相近的表达不会漏掉，同时避免把一大段无关历史塞回上下文。

## 产品视角

在长期对话中，我观察到纯向量召回容易同时出现两类问题：两三个字的中文主题、人名和项目名可能被低估；语义上略有相似但实际无关的内容又可能被召回。即使命中正确，如果一次注入过多全文，仍会消耗大量上下文并干扰当前回答。

因此我提出并定义了“字面／实体证据优先、向量补充、跨通道互证、弱命中拒绝、固定 Top-K 与字符预算、短摘要注入、原文按需核验”的产品规则。目标不是让系统想起得越多越好，而是让它每轮只想起少量、相关、可解释且可以回到原话核实的内容。

我负责提出需求、定义产品规则与验收标准；代码实现和自动化测试由 AI 完成。完整过程见 **[中文产品案例：如何让长期对话的记忆召回稳定且可信](docs/PRODUCT_CASE_ZH.md)**，与上游的能力边界见 **[CHANGES_FROM_UPSTREAM.md](CHANGES_FROM_UPSTREAM.md)**。

## 核心体验

| 使用问题 | 产品规则 | 用户可感知结果 |
| --- | --- | --- |
| 中文两字词、人名容易漏召回 | 标题、关键词、实体别名参与确定性匹配 | “奶茶”“教练”这类短词不只依赖向量理解 |
| 改一种说法后字面搜索失效 | 向量召回作为语义补充 | 没有原词时仍能找回相关记忆 |
| 弱向量相似导致乱召回 | 最低分、字面证据和跨通道互证门控 | 不因“有点像”就污染上下文 |
| 每轮注入长度波动 | 固定 Top-K、单条长度和总字符预算 | Token 消耗稳定，不突然塞入大段历史 |
| 短确认也触发检索 | 低信息消息直接跳过 | “嗯嗯”“好的”和纯标点不浪费召回成本 |
| 摘要可能失真或过期 | 摘要绑定正文 SHA-256，失效后回退正文 | 不把旧摘要当作当前事实 |
| 记忆找不到原始依据 | 记忆只绑定消息引用和内容摘要 | 普通召回保持轻量，需要时再读取原话验真 |

## 它如何工作

```text
输入消息
   │
   ├─ 去掉渠道包装与结构噪音
   ├─ 低信息消息 → 跳过
   │
   ├─ 中文词组 / 标题 / 关键词 / 实体别名 ─┐
   └─ 查询向量 / 语义相似度 ─────────────┤
                                             ↓
                                  证据门控与融合排序
                                             ↓
                              最多 3 条 + 固定字符预算
                                             ↓
                           短摘要注入；原文证据按需读取
```

向量与字面检索不是互相替代：确定性证据负责识别中文短词和专名，向量负责覆盖改写与近义表达；两者同时命中时提高置信度，只有弱向量相似时则拒绝注入。

## 原文证据绑定

这个项目把“保存原始聊天”和“证明某条记忆来自哪句话”视为两件不同的事。

- `EvidenceBinder.bind(...)` 只接受唯一精确原话或明确的消息 ID。
- 重复短句不会被猜测绑定，需要先搜索再选择具体消息。
- 绑定记录只保存消息引用、角色、时间和 SHA-256，不复制正文。
- 普通召回只显示 `available/messages`，不会自动注入旧聊天。
- 只有明确调用 `read(...)` 时才从外部对话源读取原话，并返回 `ok`、`changed` 或 `missing`。

这样既能保留审计能力，又不会让“为了可追溯”变成“每轮把历史全文再读一遍”。

## 脱敏生产观察

截至 2026 年 10 月，一套真实长期对话部署的只读元数据显示：

- 675 条有效长期记忆中，675 条具备向量，覆盖率 100%。
- 664 条具备独立短摘要，覆盖率约 98.4%。
- 37 条高价值记忆绑定了 80 条原话证据；绑定是主动选择，不追求全量覆盖。
- 常见中文短主题的命中链路约为 0.4–0.5 秒；需要外部向量补充的负例约为 1.3–1.5 秒。
- 普通注入固定为最多 3 条、总计不超过 1200 字。

这些数字来自个人长期使用系统，不是公开基准测试，也不代表其他数据集或模型上的普遍表现。本仓库只包含合成样例，不包含生产数据、聊天内容、账号、路径或凭据。

## 快速运行

项目核心只使用 Python 标准库：

```bash
python3 examples/demo.py
python3 evaluation/synthetic_eval.py
python3 -m unittest discover -s tests -v
```

演示使用 `HashingEmbedder` 验证向量接口、融合与预算逻辑。它不是生产语义模型；真实部署应替换为合适的中文 embedding 模型，并将向量存储接到 pgvector 或其他向量后端。

```python
from bounded_recall import HybridRecallEngine, RecallConfig

engine = HybridRecallEngine(
    memories,
    embedder=your_embedding_function,
    config=RecallConfig(max_hits=3, max_chars=1200),
)
result = engine.recall(user_message)
print(result.injection)
print(result.trace)
```

[`postgres/schema.sql`](postgres/schema.sql) 给出短摘要、pgvector 和原文引用表的独立示例，其中正文变化会自动清理旧摘要与旧向量。

仓库另附 4 条合成合同用例，用于直观看出三种方法的互补关系：纯字面会漏掉没有原词的改写，纯向量会在短实体和无关负例上误判，混合门控在这组刻意构造的样例中为 4/4。它只是可重复的机制演示，不是公开数据集上的效果基准。

## 验收覆盖

自动化测试覆盖：

- 低信息消息不调用向量。
- 渠道包装字段不会进入 embedding。
- 中文两字实体可以独立触发召回。
- 没有字面重合的改写可由向量补充。
- 弱向量噪音被拒绝。
- 字面与向量共同命中会留下可解释证据。
- 摘要只在正文 SHA-256 一致时使用。
- Top-K 和总字符预算不可突破。
- 唯一原话、重复短句和明确消息 ID 的绑定规则。
- 原文被修改或删除后的完整性状态。
- 绑定表不复制消息正文。

## 项目边界

- 本仓库验证召回策略和证据合同，不提供完整的聊天产品、模型服务或生产运维系统。
- `HashingEmbedder` 只能作为离线演示，不代表真实中文语义质量。
- 字符预算用于稳定上下文规模，不等于模型 tokenizer 的精确 Token 数。
- 个人生产观察尚未形成公开数据集、Recall@K 或人工标注对照实验。
- 原文证据依赖外部对话源仍然可用；源消息变化时只能报告 `changed` 或 `missing`，不会伪造恢复。
